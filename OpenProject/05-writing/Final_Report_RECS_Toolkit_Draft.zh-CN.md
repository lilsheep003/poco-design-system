# 角色扮演驱动的 UX

## 一个受 TTRPG 启发的用户需求分析工具包

**作者：** Yi Yang, Boyang Wei  
**项目：** 查尔姆斯理工大学交互设计硕士项目  
**项目背景：** 硕士论文设计与研究项目  
**主要测试产品：** Poco，一个作为论文工作一部分而设计的温和型生产力应用原型  

---

## 摘要

本报告记录了一个轻量级用户需求分析工具包的设计过程。该工具包受到桌面角色扮演游戏（tabletop role-playing game, TTRPG）的启发。项目基于 Sturdee、Gamboa 和 Heron（2023）提出的 Requirements Elicitation Campaign Setting（RECS）框架。该框架将 UX 研究会话理解为可游玩的世界：参与者扮演用户画像角色，研究者担任游戏主持人（gamesmaster, GM），而骰子机制则用于引入基于情境的复杂情况。

本项目的目标是将这一概念性方法转化为一种可在早期 UX 工作中使用的实践型研究工具。最终形成的工具包支持角色创建、情境选择、基于骰子的扰动注入、GM 笔记记录、引语捕捉，以及结构化的会话导出。Poco 是作者面向 ADHD 生产力支持方向设计的硕士论文原型，本项目将其作为设计和评估该工具包的主要测试载体。项目展示了如何将 TTRPG 结构改造为 UX 研究方法，同时不把产品测试本身变成一场游戏：参与者仍然使用真实产品，而工具包负责创造叙事距离、引入现实化干扰，并捕捉更丰富的情境数据。

## 1. 引言

用户需求分析通常依赖于让人们描述他们在做什么、需要什么，以及什么让他们感到受挫。然而，人们并不总是能够直接解释自己的需求。有些需求只有在一个人被放入具体情境、需要做出决定，并被允许自然回应压力、中断或不确定性时才会显现出来。对于支持情绪、认知或日常自我管理任务的产品而言，这一点尤其重要，因为用户体验并不只是完成一个界面流程，也包括管理注意力、信心、精力和使用情境。

本项目探索桌面角色扮演游戏中的思想是否能够支持这种 UX 研究。在 TTRPG 中，参与者并不只是回答问题。他们会承担角色，在虚构情境中行动，与其他参与者协商意义，并回应由规则或主持人引入的事件。Fine 对奇幻角色扮演游戏的社会学研究将这类游戏描述为由共同想象、规则和群体互动构建的社会世界（Fine, 1983）。Bowman 也认为，角色扮演能够支持身份探索、创造力、社会连接和问题解决（Bowman, 2010）。这些特质使 TTRPG 与 UX 研究产生关联，因为 UX 研究者同样需要处理想象中的用户、情境、动机和故障点。

本项目的直接灵感来自 Sturdee、Gamboa 和 Heron 的论文 *TTRPG UX: Requirements & Beyond*（2023）。他们提出，UX 研究可以借鉴 TTRPG 来创建“可游玩的 UX 世界”：用户画像成为角色，用户旅程成为冒险，而研究者承担类似 GM 的角色。相比于把用户当作只能成功或失败完成任务的测试对象，这种方法邀请参与者从某个角色内部探索一种情境化体验。

本项目的贡献在于构建了一个可运行的工具包，将这一想法转化为实际的研究 artefact。该工具包面向早期用户需求分析、可用性探索和设计反思。它并不替代访谈或可用性测试，而是通过加入角色扮演、情境框定和可控扰动来扩展这些方法。用于测试该工具包的主要产品是 Poco，一个作为作者硕士论文一部分创建的移动优先生产力应用原型。Poco 适合作为测试案例，因为它涉及注意力、任务启动、情绪状态和认知摩擦，而这些都需要更丰富的情境化探索。

## 2. 背景与文献

### 2.1 作为结构化想象的桌面角色扮演游戏

TTRPG 结合了规则、角色和协作式叙事。一个典型会话通常包括一位主持人，通常称为 GM。GM 负责呈现世界及其情境，而玩家则在这个世界中控制角色。规则提供结构，但事件的具体走向会通过对话、解释和决策逐步生成。

这种结构与开放性之间的平衡对 UX 研究很重要。传统研究情境可能变得过于脚本化：参与者被要求完成一个任务，研究者观察任务是否成功，然后会话继续推进。TTRPG 提供了另一种模型。情境仍然可以有结构，但参与者可以通过一个角色来解释情境，大声表达不确定性，并遭遇意外事件。Fine（1983）的研究在这里很有价值，因为他不仅将角色扮演游戏视为娱乐，也将其视为拥有自身规范、框架和互动模式的社会系统。Bowman（2010）进一步讨论了角色扮演如何帮助参与者创建社群、解决问题和探索身份。

对于本项目而言，TTRPG 的价值并不在于奇幻内容。真正有用的是其主持结构、角色框定、基于情境的行动，以及由规则支持的不确定性。

### 2.2 从游戏化到角色扮演驱动的 UX

本项目也与游戏化讨论相邻，但它并不把游戏化理解为积分、徽章或奖励。Deterding 等人（2011）将游戏化定义为在非游戏情境中使用游戏设计元素。这个定义可以作为一个宽泛的起点，但本项目采用了更窄且更具体的解释：受 TTRPG 启发的 UX 研究并不主要关于动机或娱乐，而是关于使用游戏结构来让情境化的用户体验变得可观察。

从这个意义上说，该工具包更接近角色扮演驱动的研究，而不是常规游戏化。骰子机制的加入不是为了让测试更刺激，而是为了以可控方式引入现实化干扰。角色卡的加入不是为了让参与者“升级”，而是为了创建一个可以被代入、被提问和被观察的用户画像。GM 角色的加入不是为了戏剧化会话，而是为了帮助研究者引导情境并同时捕捉数据。

### 2.3 RECS 与 TTRPG UX

Sturdee、Gamboa 和 Heron（2023）为本项目提供了核心框架。他们的论文提出了 Requirements Elicitation Campaign Setting（RECS），即 UX 研究者可以使用 TTRPG 结构来支持需求获取和用户体验工作。该论文将 TTRPG 元素映射到 UX 元素：角色对应用户画像，冒险对应用户旅程，而 GM 角色对应研究引导。

从 RECS 中继承的最重要思想是：角色扮演可以创造心理距离。当参与者以角色身份发言时，他们可能更容易描述挫败、犹豫、羞耻、困惑或抵触，因为这些表达不会让他们感到过度暴露。这对于研究那些用户状态很重要的产品尤其有用。例如，在 Poco 中，用户可能疲惫、过载、分心或自我批评。这些并不是简单的可用性变量，但它们会强烈影响产品是否真正有帮助。

RECS 论文是概念性的。它提出了 TTRPG UX 的潜力，但没有提供一个完整的可运行工具。本项目回应了这一空缺，设计了一个研究者能够在会话中实际使用的工具包。

### 2.4 以人为中心和迭代式设计

该工具包通过以人为中心和迭代式设计流程开发。ISO 9241-210:2019 将以人为中心的设计描述为一种在交互系统生命周期中持续关注用户、用户需求和要求的方法。本项目遵循这一取向，将工具包视为一个研究工具：它不仅是概念模型，也必须能够被研究者和参与者理解。

设计流程也借鉴了游戏测试实践。Fullerton 的 *Game Design Workshop* 强调通过反复使用来进行原型制作、游戏测试和系统修订（Fullerton, 2018）。这与本项目相关，因为该工具包既是一种研究方法，也是一种基于规则的体验。它的质量不能只通过阅读规则来判断，而必须在运行中测试：GM 是否能够解释它，参与者是否理解角色卡，骰子结果是否有意义，以及会话记录是否支持后续分析。

## 3. 设计目标与需求

本项目的目标是设计一个轻量级、受 TTRPG 启发的 UX 研究工具包，用于用户需求分析。该工具包应帮助研究者运行这样的会话：参与者代入用户画像角色，在与产品相关的情境中行动，并在使用真实产品的同时回应可控扰动。

该工具包围绕六项需求进行设计。

1. **支持将用户画像创建为角色。** 参与者应能够构建或调整一个带有属性、特质和简短背景故事的用户画像角色。这使会话不仅是任务式测试，也可以被角色扮演。

2. **使用基于情境的研究任务。** 工具包应以一系列节拍呈现情境。每个节拍要么设置背景，要么引入一个与真实产品操作相关的挑战。

3. **将产品表现与骰子结果分离。** 骰子不应决定参与者是否成功使用产品。产品行为仍然在真实界面中被观察。骰子只决定环境是否引入扰动。

4. **给予研究者清晰的 GM 角色。** 研究者应能够引导叙事、要求掷骰、观察参与者行为、记录笔记并捕捉引语，同时不失去对会话进程的掌控。

5. **产出可分析的会话记录。** 会话结束时，工具包应产出结构化导出内容，包括角色卡、情境、掷骰、扰动、GM 笔记、参与者引语和回顾。

6. **保持跨产品复用能力。** Poco 是主要测试载体，但工具包不应被锁定在 Poco 上。产品特定情境应放在独立的情境包中，以便其他研究者适配该方法。

## 4. 工具包设计过程

### 4.1 概念映射

第一个设计步骤是将核心 TTRPG 概念转译为 UX 研究概念。这个映射帮助定义了工具包需要包含什么。

| TTRPG 概念 | UX 研究转译 | 工具包实现 |
|---|---|---|
| 玩家角色 | 用户画像或情境化用户 | 包含属性、特质和背景故事的角色卡 |
| 属性 | 用户能力与脆弱点 | 六个面向 UX 的属性，如专注、耐心和工作记忆 |
| GM | UX 研究者或引导者 | GM 笔记本、叙事提示和实时观察工具 |
| 冒险 | 用户旅程或研究情境 | 带有逐节拍流程的情境包 |
| 掷骰 | 基于规则的不确定性 | d20 掷骰加属性修正值 |
| 复杂情况 | 现实化摩擦或中断 | 界面、认知、情绪和外部扰动库 |
| 会话日志 | 研究数据 artefact | Markdown 和 JSON 导出 |

这个映射很重要，因为它防止工具包变成一种只是带有主题包装的可用性测试。每一个 TTRPG 元素都必须服务于某个研究功能。

### 4.2 角色卡设计

角色卡是参与者进入角色扮演的入口。工具包并不是要求参与者只以自己身份进行测试，而是要求他们创建一个可信的用户角色。该角色包括姓名、角色身份、年龄、简短背景故事、设备情境、应用使用习惯，以及六个属性：

- 耐心
- 专注
- 工作记忆
- 情绪调节
- 技术素养
- 感官耐受度

每个属性评分为 1 到 5。六个属性的总点数预算为 18，这使中性角色成为可能，同时也鼓励有意识的取舍。一个参与者如果赋予角色较高的专注，可能就需要降低感官耐受度或情绪调节。这会让用户画像更具体，也让 GM 更好地理解该角色可能如何体验摩擦。

这些属性的选择是因为它们描述了经常影响数字产品使用的能力。对于 Poco 尤其如此，因为该应用面向那些可能在任务启动和认知过载方面遇到困难的用户，因此注意力、情绪调节、工作记忆和感官耐受度都很重要。

### 4.3 情境与节拍结构

每次会话都围绕一个情境展开。一个情境包含前提、目标和一系列节拍。有些节拍是叙事节拍，用于设置情绪和情境背景。其他节拍是挑战节拍，参与者需要尝试一个具体的产品操作，而 GM 会要求掷骰。

这种结构让会话保持引导性，同时不变得僵硬。研究者知道会话将走向哪里，但参与者的回应、评论和决策仍然可以改变情境的意义。

Poco 情境包包含三个情境：

- **早晨对峙（The Morning Standoff）**，聚焦于早晨任务启动、状态检查，以及选择一个任务开始。
- **被围攻的专注（Focus Under Siege）**，聚焦于开始专注会话、回应伙伴 Mochi，并在分心状态下继续任务。
- **过载思绪投放（The Overwhelmed Mind Drop）**，聚焦于捕捉散乱想法，将其中一个转化为任务，并开始行动。

这些情境之所以被选择，是因为它们符合 Poco 作为产品的核心论文观点：生产力支持不应只优化产出，也应降低开始行动时的摩擦。

### 4.4 核心设计转向：从成功判断到扰动注入

最重要的设计决策是对骰子机制理解方式的转变。

在最初的解释中，掷骰被视为成功或失败的判断。这是一种直观理解，因为许多角色扮演游戏都使用骰子来决定角色行动是否成功。然而，这对 UX 研究造成了一个问题。如果骰子决定参与者是否成功，那么工具包就开始替代产品成为评估对象。参与者可能会回应骰子，而不是回应真实界面。

最终设计采用了不同逻辑：骰子不判断产品使用是否成功，而是向环境中注入扰动。参与者仍然使用真实产品，他们的实际行为仍然是研究数据。掷骰只决定周围情境是平静、轻微受扰、显著受扰，还是受到多重扰动叠加。

这一转向让工具包更加忠实于 UX 研究的目的。产品并不是在中性真空中被测试的。用户常常是疲惫的、分心的、被打断的、不确定的，或受到情绪影响的。扰动注入为研究者提供了一种结构化方式，可以在不随机即兴的情况下引入这些条件。

### 4.5 面向 GM 的设计

该工具包主要面向研究者。参与者使用真实产品，而 GM 使用工具包引导会话。这个决定使参与者的注意力保持在被研究的产品上。

面向 GM 的部分包括：

- 每个节拍的叙事提示；
- 标明参与者应在真实产品中尝试什么的任务提示；
- 掷骰控制；
- 扰动结果；
- 用于实时观察的 GM 笔记本；
- 带时间戳的引语捕捉；
- 掷骰与扰动日志；
- 总结与导出页面。

这使工具包不仅是一个类似游戏的层，也是一种研究捕捉工具。

## 5. 最终设计成果

### 5.1 会话流程

最终工具包遵循五阶段会话流程。

| 阶段 | 目的 | 主要输出 |
|---|---|---|
| 设置 | 准备会话和参与者编号 | 会话身份与检查清单 |
| 角色 | 构建用户画像角色 | 角色卡与属性画像 |
| 情境选择器 | 选择产品包和情境 | 当前研究情境 |
| 情境运行 | 推进叙事节拍和挑战节拍 | 掷骰、扰动、笔记和引语 |
| 总结 | 回顾并导出会话 | Markdown 和 JSON 会话记录 |

该流程被设计为让研究者能够在一次会面中带领一名参与者完成一个情境。工具包并不试图自动化分析。相反，它产出一份清晰记录，之后可用于主题分析，或与传统可用性测试数据进行比较。

### 5.2 骰子与扰动系统

骰子系统使用 d20 掷骰加属性修正值。修正值根据角色的属性数值计算。难度等级设置为三级：简单、中等和困难。结果被分为五个区间：

| 结果 | 在工具包中的含义 |
|---|---|
| 平静 + 小优势 | 环境格外友好；不引入扰动 |
| 平静 | 参与者自然继续 |
| 轻微扰动 | 引入一个小型干扰 |
| 显著扰动 | 引入一个更强的干扰 |
| 复合扰动 | 引入多个或严重干扰 |

关键在于，这些结果描述的是环境，而不是参与者的能力。例如，如果一个角色在 Poco 专注会话中未通过专注检定，这并不意味着参与者不会使用 Poco。它意味着环境现在引入了一个分心因素，例如通知、侵入性想法或伙伴事件。随后研究者观察参与者对该干扰的回应。

### 5.3 复杂情况库

工具包包含一个不绑定具体产品的复杂情况库，共有四类：

- **界面：** 意外的系统行为、不清晰的控件或布局变化。
- **认知：** 记忆中断、决策瘫痪或忘记原本意图。
- **情绪：** 自责、羞耻、挫败或感觉被注视。
- **外部：** 设备之外的中断，例如通知或他人说话。

每个复杂情况都有严重程度。轻微扰动会抽取低严重程度的复杂情况，而显著或复合扰动可以抽取更高严重程度的复杂情况。产品包也可以添加产品特定的复杂情况。例如，Poco 情境包包含与 Mochi、状态标签、心情/精力/专注检查，以及任务拆解流程相关的复杂情况。

### 5.4 Poco 作为主要测试载体

Poco 并不是一个随意选择的例子。它是作者的硕士论文设计作品：一个温和型生产力应用原型，面向那些在启动任务、管理状态和维持专注方面经历摩擦的人。它的核心交互包括状态检查、任务拆解、Mind Drop、专注会话，以及一个小型伙伴角色 Mochi。

Poco 是该工具包的强测试载体，原因有三点。第一，该产品处理精力、专注、过载和情绪阻抗等主观状态。第二，它的价值取决于它在混乱的日常条件下如何运作，而不仅仅取决于干净条件下的任务完成。第三，它的设计已经包含情境丰富的时刻：早晨选择任务、进入专注模式、回应伙伴反馈，或把想法投放到收件箱中。

使用 Poco 使工具包能够在一个真实论文 artefact 上被测试，同时仍然保留工具包的通用目的。该工具包可以运行其他产品包，但 Poco 提供了主要设计语境和试点情境集。

### 5.5 研究输出

一次工具包会话的最终输出是一份结构化记录。Markdown 导出用于人工阅读和质性分析。JSON 导出则保留完整会话对象，以便未来进行可能的聚合。

导出内容包括：

- 参与者编号；
- 已选择的产品包和情境；
- 完整角色卡；
- 属性数值；
- 每一个经历过的节拍；
- 所有掷骰和结果；
- 被注入的复杂情况；
- 压力和 UXP 变化；
- GM 实时笔记；
- 参与者引语；
- 会后回顾。

该输出很重要，因为这种方法的价值不仅在于让会话更有参与感，也在于产出会后可以分析的数据。

---

## 6. 测试与评估过程

### 6.1 自动化冒烟测试

第一层测试是使用 Playwright 进行的内部冒烟测试。该测试从空浏览器存储状态开始，打开工具包，输入参与者编号，创建用户画像名称，选择情境包，选择一个 Poco 情境并启动会话。测试会检查主界面是否渲染、每个阶段是否出现预期控件，以及是否没有 JavaScript 控制台错误或页面错误。

该测试不能证明研究方法是有效的，但它可以验证工具能够端到端运行而不发生基本功能故障。对于研究工具而言，这一点很重要，因为损坏的会话流程可能破坏参与者数据的质量。

### 6.2 内部演练

第二层测试是论文作者之间的内部演练。在该测试中，一位作者担任 GM，另一位作者担任参与者。目标是检查方法在使用中的表现，而不仅仅是界面。

演练应关注：

- Session Zero 是否容易理解；
- 参与者是否能够创建并代入一个角色；
- 属性解释是否清晰；
- 情境节拍的节奏是否合适；
- 骰子结果是否感觉有意义，而不是任意的；
- 扰动是否产生有用的观察；
- GM 是否能够在引导的同时捕捉笔记和引语；
- 导出的记录在会后是否可读。

这一阶段最接近游戏测试。它检查的是方法的流程、时间安排和体验感。

### 6.3 试点测试

第三层是在任何更大规模研究之前，与一到两名交互设计同学进行试点测试。这些参与者不需要是 Poco 的最终目标用户。他们的作用是暴露工具包本身的问题：不清楚的说明、令人困惑的术语、尴尬的 GM 脚本、过长的节拍、较弱的扰动或缺失的导出数据。

试点反馈应通过观察和简短回顾收集。有用的问题包括：

- 参与者是否理解自己与角色之间的区别？
- 角色扮演是让他们更容易还是更难谈论产品体验？
- 骰子机制感觉有用、分散注意力，还是不公平？
- 扰动是否感觉真实？
- GM 角色是否可管理？
- 会话是否产生了普通可用性测试可能遗漏的发现？

试点应促成工具包修订，然后再进入主要评估。

### 6.4 主要研究方向

更大规模的评估可以使用 Poco 比较 RECS 风格会话与更传统的可用性测试会话。这种比较不需要证明某一种方法普遍更好。更现实的目标是识别每种方法会产生什么类型的洞察。

作为基线，传统会话可以遵循可用性工程实践，关注任务成功、任务用时、可用性问题和出声思考评论（Nielsen, 1993）。RECS 会话可以关注情境化需求、情绪回应、角色扮演反思、扰动回应和 GM 观察。比较两者可以显示受 TTRPG 启发的方法是否揭示了不同类型的数据。

### 6.5 需要收集的数据

研究可以结合质性和量化数据。

质性数据：

- 参与者在会话中的评论；
- GM 笔记；
- 会后回顾回应；
- 被观察到的犹豫、困惑或情绪反应；
- 关于角色和情境的反思。

量化或结构化数据：

- 任务完成情况；
- 任务用时；
- 掷骰结果；
- 扰动的数量和类型；
- 压力计数；
- UXP 使用情况；
- 参与者对清晰度、参与感、舒适度和感知真实感的评分。

主要分析应关注洞察质量：该方法揭示了什么，发现有多具体，以及这些发现是否能够为 Poco 或类似产品的设计决策提供依据。

## 7. 讨论

该工具包的主要价值在于让用户需求更加情境化。它不是要求参与者抽象地陈述需求，而是把一个角色放入某个时刻：醒来晚了、试图开始工作、失去专注、收到通知、被优先级标签评价，或者判断一个伙伴角色是让人安心还是令人烦躁。这些时刻能够揭示通过直接提问很难触及的需求。

对于 Poco 来说，这一点尤其相关。该应用的设计挑战不仅是按钮是否可见，或屏幕是否容易理解。问题在于，当用户疲惫、思绪分散、感到羞耻、犹豫不决或过载时，产品是否还能提供帮助。受 TTRPG 启发的工具包为研究者提供了一种探索这些状态的方式，而不迫使参与者只从个人脆弱性出发发言。角色创造距离，而情境让会话保持具体。

扰动机制也有用，因为它引入了可控的混乱。传统可用性测试往往发生在安静且人为的条件下。真实使用并非如此。用户可能收到消息，忘记自己为什么打开应用，产生自我批评，或被附近的人打断。该工具包并不模拟每一种真实世界条件，但它允许研究者一致地引入其中一部分。

该方法也存在限制。它依赖引导能力。一个过度表演虚构情境的 GM 可能会使注意力偏离产品，而一个解释规则不足的 GM 可能会让参与者困惑。有些参与者可能会觉得角色扮演陌生或不舒服。由于角色创建和情境框定需要时间，会话也可能比标准可用性测试更长。

从伦理角度看，该方法需要谨慎。由于扰动可能包含情绪压力，研究者必须避免让参与者感到被评判或被困住。角色框架应当保护参与者，而不是操控他们。参与者应能够暂停、退出角色或停止会话。

因此，该方法最适用于研究问题涉及情境化行为、情绪回应、复杂背景或早期需求探索的情况。如果目标只是发现简单界面错误，或测量一个狭窄任务的完成率，那么它就不那么适合。

---

## 8. 结论

本项目设计了一个受 TTRPG 启发的 UX 研究工具包，用于用户需求分析。基于 RECS 以及有关角色扮演、游戏化和迭代设计的相关研究，本项目将 TTRPG 概念转译为一种实践型研究工具。最终工具包包括用户画像角色创建、基于情境的任务流程、由骰子驱动的扰动注入、GM 笔记记录，以及结构化会话导出。

最重要的设计决策是将掷骰视为环境扰动，而不是成功判断。这使真实产品保持在研究会话的中心，同时让研究者能够引入现实化干扰。参与者的行为、评论和恢复策略仍然是真正的数据。

Poco 是作者的硕士论文原型，并作为主要测试载体。它对任务启动、情绪状态和注意力的关注，使其成为探索该工具包的有力语境。同时，工具包通过情境包保持产品无关性，因此未来研究者可以将其适配到其他产品。

下一步是完成试点测试，然后比较 RECS 风格会话与传统可用性测试。预期贡献并不是宣称 TTRPG 方法应当替代现有 UX 方法，而是更清楚地理解：在什么时候，角色扮演驱动的研究能够揭示标准方法可能遗漏的需求、张力和情境化行为。
